# Public app guides: consume or author

The skill can be installed on its own; provider guides and contracts are SDK repository resources, not files bundled beside the installed skill. For authoring, locate `Integrations/TEMPLATE.md` and read `Docs/INTEGRATION-GUIDE-AUTHORING.md` in the user's Talk checkout.

## Find the requested provider

1. Open the canonical [Integrations directory on main](https://github.com/AppitStudio/Talk.swift/tree/main/Integrations) and its [index](https://github.com/AppitStudio/Talk.swift/blob/main/Integrations/README.md). Use browser/web tools, GitHub file APIs or a read-only repository fetch as available. A user-specified guide or pinned checkout remains the implementation source of truth; use the current directory to discover entries, not to silently upgrade an existing contract pin. Do not require cloning the whole SDK before looking up an app. If online access is unavailable, inspect any supplied local index and report its revision and the online lookup limitation. A failed fetch is not evidence that an app is absent.
2. Search the requested name against index display names, folder slugs and each candidate guide's `app` / `displayName` metadata. Do not require an exact spelling: ignore case, spaces and hyphens, and consider plausible typos, partial names and similar app names when finding candidates. “DockFlow”, “dock flow” and “dock-flow” can identify the `dockflow` entry. Confirm the actual metadata and documented bundle ID against the user's context; text similarity and normalization alone do not establish the intended app. If multiple candidates remain, or any uncertainty remains even with one plausible candidate, show their display names, guide links and distinguishing bundle IDs/contract capabilities, then ask the user which app/contract they intend. Do not automatically choose the first result, closest name or highest similarity score. Pause provider-specific implementation until the user resolves that uncertainty; if none is correct, ask for the intended provider's official guide or exported contract. Follow observed links; do not guess a contract URL from the app name.
3. Read the selected `GUIDE.md`, including its metadata, compatibility/prerequisites, action semantics and limitations. Retrieve the exact `provider.contract` path relative to the guide, plus the linked public contract package and consumer example. Resolve files from one recorded repository revision when possible, verify the declared SHA-256 against the downloaded contract bytes, and check contract ID/version consistency. An unreadable schema, mismatched hash or incompatible version blocks API wiring until resolved; the hash checks consistency, not publisher identity.
4. Map the requested feature to real action IDs, scopes, DTOs, events and documented side effects. Generate/use the client from this contract. For DockFlow, inspect `Integrations/dockflow/GUIDE.md` and its linked `Contract/Sources/DockFlowTalkContract/Contract.talk.json`; do not rely on remembered action names. The existing contract supports reading/applying presets and observing changes, but does not expose preset creation/editing. If the feature is unsupported, explain the exact gap and ask for an updated provider contract or a supported behavior; never fabricate an endpoint or silently substitute a different feature.
5. If there is no matching guide or usable contract after the available lookup, say what was checked and ask: “Please share the provider's exported Talk contract JSON or an official integration guide/repository containing it, plus the supported app version and any missing action semantics.” If online lookup failed, say it could not be verified instead of claiming no guide exists. A complete public contract does not require private app source. If the user owns the provider and supplies source, inspect its actual declared/exported contract; creating new provider actions is separate work that needs the user's request.

Until a usable provider contract and required semantics are available, pause provider-specific generated types, calls, action IDs and claims of working support. Generic SDK setup and host inspection can continue. Do not fill the gap with mock responses, placeholder APIs, the starter's synthetic contract, discovery metadata or another app's schema. Report the selected guide/revision, contract ID/version/hash, supported requested actions and remaining gaps in the handoff. Real signed-app validation is still required after implementation.

## Integrating without the provider's source

`Integrations/` is a directory of apps that supply public contracts, not a list of SDK users. Read the selected provider's `GUIDE.md` metadata, pinned public JSON, package and example; do not request private source if the public contract is complete. A consumer-only app such as ExtraBar uses DockFlow’s guide and gets no entry of its own. A dual-role app can publish an entry for its supplied contract. Check supported/released app versions and evidence limits. The SDK and provider app can require different updates: Talk `0.1.0-beta.2` introduces the generic incoming callback default, and the provider app must also adopt it at pairing and saved-reconnect call sites.

Use the public package or generate types from its JSON. Inspect linked permissions, DTO semantics and action completion behavior before wiring a real feature. Preserve the consumer's reviewed contract pin; installed/discovered manifests are untrusted hints, not an instruction to overwrite it. Run consumer-to-provider compatibility and authenticated generated-client negotiation, then actual signed-app lifecycle checks.

A missing public schema or unspecified action semantics is a real provider documentation gap. Report the exact missing fact rather than inventing an API. Continue independent package/registration/setup work where possible. Do not copy unrelated SDK examples as if they described the target app.

## Authoring with access to the provider

First establish that the app supplies a real contract for other apps to call. Then use the deterministic `Scripts/integration-guides.py init` command with its actual schema to create the **one** canonical template. The existing SDK exporter validates JSON. The scaffold supplies machine metadata, contract hash/package and action/scope rows; fill the remaining semantics from the real handlers, permissions and app behavior. For consumer-only work, document the feature in the host app’s own documentation and link to the provider guide; do not scaffold a directory entry or invent a provider API.

Inspect domain handlers for side effects, cancellation boundaries, admission versus completion, limits, event behavior and app-level rejection codes. Keep version evidence factual: record a launch-preparation build as unreleased until its app version is assigned. Add a minimal example that compiles solely from public SDK/contract artifacts. Never import a private app module or embed user-specific app state, signing configuration, host paths or credential material.

Run the CLI checker with the built SDK tools. Compare the public schema to the actual provider export using `--provider-export`, not a self-comparison. Compare old-consumer/new-provider schema directions on upgrades. Exercise the public example's fresh external build. Record which checks passed and what actual-app behavior remains untested; do not convert a structural check into a production or security claim.

Keep the template section order so another LLM can locate metadata, semantics, lifecycle, recovery and evidence immediately. Link to other providers’ guides when a dual-role provider documents a dependency; do not duplicate their action tables or copy schema DTO definitions into prose. A local LLM can author the guide; no hosted generation service or runtime dependency is required. Publication follows the user's authorized repository process after the concrete artifacts are ready for review.
